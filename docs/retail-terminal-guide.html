Retail EGM integration

This guide is for the team building the EGM side: the terminal software in or beside each cabinet, which handles the credit meter, the bill validator, AFT and the cash-out button.

EGM API · you host it

It holds the balance. The Game Engine API calls it to read the balance and to debit bets and credit wins.

Game Engine API · we host it

It runs the game. You call it when money arrives at or leaves the cabinet: notes, AFT and cash-outs.

01How it works

  • Your meter is the balance. The Game Engine API keeps no balance of its own. It asks your EGM API every time.
  • Bets and wins arrive as calls to your EGM API. You apply them to the meter and return the new balance.
  • Notes, AFT and cash-outs are reported to us. That way the game on the cabinet's screen updates straight away. For a cash-out, we also confirm that no bet is still in play.

02How debit and credit work

There is one endpoint on your side. Every call carries the EGM id, a debit and a credit. You apply both to the meter and return the balance afterwards.

What happens in the gameCall to your EGM APIMeter
The game opens, reconnects or shows the balancedebit: 0, credit: 0
Balance		No change. You return the balance.
The player places a betdebit: stake, credit: 0
Debit		− stake. If the meter is too low, answer 402 INSUFFICIENT_FUNDS.
The player wins (cashes out in time)debit: 0, credit: win
Credit		+ win. The win includes the stake (a stake of 10 cashed out at 1.10x gives a credit of 11).
The player loses (the round crashes first)No callThe stake is already gone.
A bet is refunded (the round closed while it was being placed)debit: 0, credit: stake
Rollback with relatedTransactionId		+ stake. If you never booked that bet, refund nothing.

The rules for every call:

  1. transactionId is an idempotency key. We send the same id again when a call times out. If you have already booked it, don't book it again: answer 200 with the current balance and duplicate: true. If the id comes back with a different debit or credit, answer 409 REFERENCE_CONFLICT.
  2. Apply the call atomically. Check the meter, change it and record the transaction as one operation. Two bets can arrive at the same moment, one for each betting slot.
  3. Answer within 5 seconds. After a timeout we retry up to 3 times with the same id. If a bet still fails, it isn't placed. If a win still fails, the player is told to try again and we log it for reconciliation.
  4. Never pay out from a game call. Debits and credits only move the meter. Money leaves the cabinet only through a cash-out.

The ids we send look like BET_<32 hex>, WIN_<32 hex> and ROLLBACK_BET_<32 hex>. A bet and its win share the same hex part, so you can match them. Treat them as opaque strings of up to 100 characters.

Bill_Inserted

Send this after the note is stacked and you have added it to your meter. The game shows the new balance straight away with a "Credits added" message. If this call fails, the money is still safe on your meter; the game picks the balance up on its next read.

// request
{
  "egmId": "EGM1",
  "event": "Bill_Inserted",
  "amount": 200,
  "transactionId": "EGM1-BILL-000123",
  "balance": 200.00
}
// 200
{
  "egmId": "EGM1",
  "event": "Bill_Inserted",
  "transactionId": "EGM1-BILL-000123",
  "amount": 200.00,
  "balance": 200.00,
  "currency": "ZAR",
  "timestamp": "2026-11-10T14:35:05.0894700Z"
}

Cashout

  1. Lock the meter against debits. Until step 5, answer any Debit to your EGM API with 423 EGM_LOCKED. Keep accepting Credit and Rollback, because a bet that is still riding must be able to pay out.
  2. Call Cashout.
  3. On 409 ROUND_IN_PROGRESS, a bet is still in play. Show "Finishing game…" and repeat step 2 every 1–2 seconds.
  4. On 200, amount is the game's balance. The game now shows R0.00.
  5. Pay out your meter, set it to 0, record the payout and unlock. Your meter and amount should match. If they don't, pay your meter (it is the balance) and log the difference for us.
// request
{
  "egmId": "EGM1",
  "event": "Cashout",
  "transactionId": "EGM1-CASHOUT-000045"
}

// 409 while a bet is riding
{
  "error": "ROUND_IN_PROGRESS",
  "message": "A bet is in play on this EGM — retry the cash-out when the round ends."
}
// 200 once the round has ended
{
  "egmId": "EGM1",
  "event": "Cashout",
  "transactionId": "EGM1-CASHOUT-000045",
  "amount": 251.00,      ← pay this
  "balance": 251.00,
  "currency": "ZAR",
  "timestamp": "2026-11-10T14:35:31.8360201Z"
}

Balance

This returns the balance as the game sees it. It always matches your meter, because we read it from your EGM API. Use it as a health check of both directions.

// request
{ "egmId": "EGM1", "event": "Balance" }
// 200
{
  "egmId": "EGM1",
  "event": "Balance",
  "transactionId": null,
  "amount": 0,
  "balance": 0.00,
  "currency": "ZAR",
  "timestamp": "2026-11-10T14:35:33.5478834Z"
}

08Test sequence

Against our staging API, with your EGM API reachable from it:

API=https://<retail-api-host>; KEY='<terminal key>'
call() { curl -s -X POST "$API/api/retail/terminal" -H "Content-Type: application/json" -H "X-Terminal-Key: $KEY" -d "$1"; echo; }

call '{"egmId":"EGM1","event":"Balance"}'                                                    # proves we can read your EGM API
call '{"egmId":"EGM1","event":"Bill_Inserted","amount":100,"transactionId":"T-BILL-1","balance":100}'
call '{"egmId":"EGM1","event":"Cashout","transactionId":"T-CO-1"}'                           # amount = your meter

Then, with the game open at <GameUrl>?egmid=EGM1:

  1. Insert a note. The game's balance updates within a second.
  2. Bet R10. Your EGM API receives a Debit of 10 and the meter drops by 10.
  3. Cash out in the game before the crash. Your EGM API receives a Credit that includes the stake.
  4. Press cash out on the cabinet while a bet is riding. You get 409 ROUND_IN_PROGRESS, then 200 once the round ends.
  5. Make your EGM API time out once on a Debit. You receive the same transactionId again, and the meter must only drop once.

09Checklist

  • The EGM API's /wallet endpoint is live, reachable from our API, and checks X-Api-Key.
  • Debit and credit are applied atomically and return the balance after the call.
  • transactionId is idempotent: a repeat returns 200 with duplicate: true and changes nothing.
  • A debit larger than the meter answers 402 INSUFFICIENT_FUNDS.
  • A rollback for an unknown bet refunds nothing and answers 200.
  • The endpoint answers within 5 seconds.
  • The cabinet's browser opens <GameUrl>?egmid=<id>, and each EGM id is registered with us.
  • Bill_Inserted and AFT_Deposit are sent after the meter is updated, ideally with balance.
  • Cash-out locks debits, retries on 409, pays the meter, and then unlocks.
  • Amounts are in currency units (not cents), with at most 2 decimal places.
